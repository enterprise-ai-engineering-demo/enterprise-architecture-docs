# REST API reference

This reference describes **implemented backend behavior**, defined in
`customer-management-api/src/app.js`, `src/customers.js`, `src/auth.js`, and
`src/errors.js` at the [recorded baseline](architecture.md#source-baseline).
It is not the richer contract expected by the frontend.

## Conventions and endpoint inventory

Default origin: `http://localhost:4000`. `/health` is outside the `/api` prefix.
Examples assume the local API is running and `TOKEN` holds a locally generated,
unexpired demo token; see [setup](local-setup.md).

| Method | Full path | Authentication | Success | Request body |
| --- | --- | --- | --- | --- |
| GET | `/health` | Public | 200 | None |
| GET | `/api/customers` | Bearer JWT | 200 | None |
| GET | `/api/customers/:id` | Bearer JWT | 200 | None |
| POST | `/api/customers` | Bearer JWT | 201 and `Location` | Customer JSON object |

This is the complete registered application endpoint set. No login, refresh,
logout, user, role, JWKS, update, delete, search, or reporting endpoint exists.
`shared-auth-platform` exposes no REST endpoints. SPA routes are not REST APIs.
There is no configured CORS/OPTIONS integration contract.

Successful responses use `{ "data": ... }`. Failures use
`{ "error": { "code": "...", "message": "...", "details": [...] } }`,
with `details` only when supplied by field validation.

### Backend customer schema

| Field | Request rule | Returned value |
| --- | --- | --- |
| `id` | Rejected as an unknown input field | UUID string generated by `randomUUID()` for new records |
| `name` | Required string, nonempty after trimming, maximum 100 characters after trimming | Trimmed string |
| `email` | Required string, maximum 254 characters after trimming; must match `^[^\s@]+@[^\s@]+\.[^\s@]+$` | Trimmed lowercase string, unique within this app instance |
| `company` | Optional; if present, must be a nonempty string of at most 200 characters after trimming | Trimmed string, or omitted if not provided |

Only `name`, `email`, and `company` are accepted in POST. The lengths are
JavaScript string lengths, not byte counts. Unknown fields are rejected, not
silently stripped. There are no returned `status`, `createdAt`, `phone`, or
`industry` fields.

## GET /health

Public liveness request; no body or query parameters are required.

```bash
curl -i http://localhost:4000/health
```

HTTP **200**, JSON:

```json
{
  "data": {
    "status": "ok"
  }
}
```

This is not a storage, authentication-provider, CORS, or frontend readiness check.
Server startup still requires valid JWT configuration.

## GET /api/customers

Returns all customers. No implemented query filtering, sorting, or pagination
exists. Extra query parameters are not used by the handler.

```bash
curl -i http://localhost:4000/api/customers \
  -H "Authorization: Bearer $TOKEN"
```

HTTP **200** on a fresh process:

```json
{
  "data": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "name": "Alex Morgan",
      "email": "alex.morgan@example.com",
      "company": "Northwind Demo"
    },
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "name": "Jordan Lee",
      "email": "jordan.lee@example.com",
      "company": "Contoso Demo"
    }
  ]
}
```

Created records are appended for the lifetime of that app instance. No total,
page, or cursor metadata is returned.

## GET /api/customers/:id

Looks up an exact string ID. There is no separate UUID-format validation;
an unknown identifier returns 404.

```bash
curl -i \
  http://localhost:4000/api/customers/11111111-1111-4111-8111-111111111111 \
  -H "Authorization: Bearer $TOKEN"
```

HTTP **200**:

```json
{
  "data": {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "Alex Morgan",
    "email": "alex.morgan@example.com",
    "company": "Northwind Demo"
  }
}
```

An authenticated request for `/api/customers/unknown` receives HTTP **404**:

```json
{
  "error": {
    "code": "CUSTOMER_NOT_FOUND",
    "message": "Customer not found."
  }
}
```

## POST /api/customers

Requires `Content-Type: application/json` and a JSON object. The customer router
authenticates before parsing JSON. Its JSON parser limit is `16kb` (16,384 bytes);
no route-specific multipart or form parser is configured.

```bash
curl -i http://localhost:4000/api/customers \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":" Taylor Smith ","email":"TAYLOR@example.com","company":" Demo Corp "}'
```

HTTP **201**, with
`Location: /api/customers/33333333-3333-4333-8333-333333333333`.
The ID below is illustrative; the server generates a different UUID:

```json
{
  "data": {
    "id": "33333333-3333-4333-8333-333333333333",
    "name": "Taylor Smith",
    "email": "taylor@example.com",
    "company": "Demo Corp"
  }
}
```

A body `{"name":"Sam Demo","email":"sam@example.com"}` is also valid; the
response omits `company`. An empty string or `null` company is not equivalent to
omitting it.

Sending `{"name":"","email":"valid@example.com"}` receives HTTP **400**:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Customer validation failed.",
    "details": [
      {
        "field": "name",
        "message": "Must be a non-empty string of at most 100 characters."
      }
    ]
  }
}
```

Repeating a successful email, including a differently cased version, receives
HTTP **409**:

```json
{
  "error": {
    "code": "CUSTOMER_EXISTS",
    "message": "A customer with this email already exists."
  }
}
```

There is no idempotency key implementation. Do not automatically retry a POST
after a lost response: first check whether its email already exists.

## Error behavior

| Status | Code | Exact message / condition |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | `A JSON object is required.` for missing/non-object body reaching the validator |
| 400 | `VALIDATION_ERROR` | `Customer validation failed.` with field `details` |
| 400 | `INVALID_JSON` | `Request body must be valid JSON.` for malformed JSON or parser-rejected JSON primitives |
| 401 | `UNAUTHORIZED` | Missing/malformed bearer authentication or invalid/expired JWT; see [authentication](authentication.md) |
| 404 | `CUSTOMER_NOT_FOUND` | `Customer not found.` |
| 404 | `NOT_FOUND` | `Route not found.` for unmatched routes/methods after applicable middleware |
| 409 | `CUSTOMER_EXISTS` | `A customer with this email already exists.` |
| 413 | `PAYLOAD_TOO_LARGE` | `Request body exceeds the 16 KB limit.` |
| 415 | `UNSUPPORTED_ENCODING` | `Request body encoding is not supported.` for parser errors with status 415 |
| 500 | `INTERNAL_ERROR` | `An unexpected error occurred.`; original error logged server-side |

Field detail messages are `Unknown field.`,
`Must be a non-empty string of at most N characters.`, and
`Must be a valid email address.` as applicable. Multiple details can be returned
for one request. Arrays reach object validation and are rejected; primitives
such as `null` sent as JSON may be rejected by the strict JSON parser first.
An unsupported or missing content type is not a dedicated 415 media-type
contract: if parsing is skipped, POST reaches the missing-object validation.

No authorization-specific 403 is emitted by the implemented middleware, although
the frontend has generic handling for that status. Unauthenticated requests under
`/api/customers` can return 401 before a missing route or malformed body is
considered. For example, an OPTIONS preflight is not a supported CORS exchange.

## Frontend contract incompatibility

The actual frontend interfaces are in `customer-portal-frontend/src/types/customer.ts`;
runtime validation is in `src/services/customers.ts`.

```ts
type CustomerStatus = 'active' | 'pending' | 'inactive'

interface Customer {
  id: string | number
  name: string
  email: string
  company: string
  phone?: string
  industry?: string
  status: CustomerStatus
  createdAt: string
}

interface CreateCustomerInput {
  name: string
  email: string
  company: string
  phone: string
  industry: string
  status: CustomerStatus
}
```

The runtime check requires `createdAt` to be a string parsable by `Date.parse`,
and `status` to be one of the three named values. It requires `company` to be a
string even though the backend allows omission.

| Surface | Frontend behavior | API behavior | Current result after transport/auth succeeds |
| --- | --- | --- | --- |
| List/detail | Requires `status`, `createdAt`, string `company` | Returns no status/date; company optional | Visible unexpected customer format error |
| Creation | Sends all six input fields; optional form values become empty strings | Only three fields accepted | 400 unknown-field details for `phone`, `industry`, `status` |
| Create response | Requires full frontend `Customer` | Returns backend customer shape | Still rejected if only the POST input were adapted |
| Company | Required nonblank by creation form | Optional but nonblank if present | Different business contract |
| Envelope | Accepts raw values or `data` | Always returns `data` | Compatible |
| Identifier | Accepts string or number; URL-encodes lookup | Returns/looks up strings | Current UUIDs compatible |
| Errors | Maps status to UI text, does not consume error body | Returns structured codes/details | Detailed field/duplicate explanations lost in UI |

For example, the frontend sends the following payload, which is **not accepted**
by the current backend:

```json
{
  "name": "Taylor Smith",
  "email": "taylor@example.com",
  "company": "Demo Corp",
  "phone": "",
  "industry": "",
  "status": "active"
}
```

Choosing a unified contract is proposed work. Do not fabricate `createdAt` or
`status` in documentation or an adapter and present them as stored backend data.
See [change management](integration-risks.md).
